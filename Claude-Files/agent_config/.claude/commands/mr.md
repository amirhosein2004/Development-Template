Single entry point for everything MR-shaped in the workspace. Routes by the first positional argument to `open` (stage+commit+push+open MR, stop after report), `ship` (same, then wait-for-mergeable + squash-merge + ff-pull + cleanup), or `format` (the operative MR/branch/commit shape reference that other skills load via `[[mr]]`). Assumes the standard workspace shape (`business/`, `product/`, `tech/`, plus a docs container `<config-dir>` — typically `docs/`, plus **optionally** a `scripts/` folder holding bootstrap / tooling repos) discovered at call time — no hardcoded repo list.

## Workspace repo discovery

Every scope resolution below runs the same on-disk discovery. Discover at call time; any repo added later surfaces automatically.

```sh
ls -1d <workspace-root>/<config-dir> \
        <workspace-root>/business/docs \
        <workspace-root>/product/docs \
        <workspace-root>/tech/docs \
        <workspace-root>/tech/*/ \
        <workspace-root>/scripts \
        <workspace-root>/scripts/*/ 2>/dev/null
```

**`scripts/` handling** (workspace-tooling folder, present in some projects, absent in others — always probe):

- If `<workspace-root>/scripts/` does not exist → skip; not every project ships a scripts folder.
- If `<workspace-root>/scripts/.git` exists (directory or file) → `scripts/` is itself a single git repo (Avakav-style workspace-tooling layout). Treat as one repo whose workspace-relative path is `scripts`.
- Otherwise, if `<workspace-root>/scripts/*/` contains subdirectories with their own `.git` → each is an independent repo (tizvir-style `scripts/initializer/`, `scripts/<other-tool>/`). Enumerate every immediate subdirectory whose `.git` exists; each is a repo whose workspace-relative path is `scripts/<name>`.
- Both patterns can coexist in principle (though rare); enumerate whichever `.git` entries actually exist.

Scripts repos participate in `touched` / `all` / `<repo-path>` scopes exactly like any other repo — same default-branch resolution via `git symbolic-ref --short refs/remotes/origin/HEAD`, same commit / push / MR flow, same body template. `current` scope naturally picks a scripts repo when cwd is inside it.

## Synopsis

```
/mr <open|ship> <touched|all|current|<repo-path>>
/mr format
```

| Sub-op | Anchor | One-liner |
|---|---|---|
| `open` | [`## open`](#open) | Stage explicit paths, conventional-commit, push, open MR — stop after the report. |
| `ship` | [`## ship`](#ship) | Same as `open` plus wait-for-mergeable, squash-merge, ff-pull the repo's default branch, clean up the worktree/branch. |
| `format` | [`## format`](#format) | The operative MR/branch/commit shape reference — pre-flight chain, body template, mirror/hotfix variants, hard rules, self-check. |

If the first arg is missing or not one of `open` | `ship` | `format`, stop and ask — never default. For `open` and `ship`, if the scope arg is missing or not one of `touched` | `all` | `current` | `<repo-path>`, stop and ask — running `all` by accident is too costly to undo.

Full procedure for every sub-op lives in [`skills/mr/SKILL.md`](../skills/mr/SKILL.md). This file is the router.

## Hard rules (every mode, every scope)

- **No `Co-Authored-By:`** footers — on commits or MR body.
- **No direct push** to a protected branch (per the workspace's own git standards — typically `main`, `staging`, `develop`). Always MR back. `bash-guard.sh` rejects violating pushes.
- **No bulk staging** — `git add -A`, `git add --all`, `git add .`, `git add *` are all forbidden (also enforced by `bash-guard.sh`). Stage explicit paths.
- **No `--no-verify` / `--no-gpg-sign`.** Fix the underlying hook or signing failure.
- **No secrets** — no `.env*`, `*.pem`, `*.key`, `*.p12`, `credentials.json`, `service-account*.json`, kubeconfigs, API tokens, or anything the standard `.gitignore` would catch.
- **No `glab mr create --fill`.** Always pass the body via `--description "$(cat <tmp-body-file>)"`.
- **No mentions of `CLAUDE.md` / `README.md`** from an MR body or doc — inline the content.
- **No Claude / agent attribution**, no emoji (unless the change is about emoji), no "Generated by …" lines in the MR body.
- **No unrelated changes** in one MR. One concern per MR.
- **Only `[x]` features** from `<workspace-root>/product/docs/features/v<N>/all-features.md` (highest `v<N>` present) are in scope. A `[ ]` feature reaching the diff is a stop-and-ask.
- **Engineering only:** a `feature` MR without a test is an automatic block in review.
- **Project-specific hard rules** — schema invariants, locale rules, scope gates, reserved-slot guards — live in the workspace's own per-project sibling hooks under `<config-dir>/.claude/hooks/`, layered on top of the two generic guards this bundle ships (`bash-guard.sh`, `write-edit-guard.sh`). `/mr` surfaces the block message unchanged.

## open

Stage explicit paths, conventional-commit, push, open MR via `glab`, stop after the report. The scope arg selects which repos qualify.

### Argument

`/mr open <touched|all|current|<repo-path>>`

- `touched` — only repos this session edited. Source of truth is conversation context; empty list → stop with "nothing touched this session".
- `all` — scan every discovered workspace repo (count varies per project) and open MRs wherever there are pending changes.
- `current` — single-repo mode targeting the repo containing cwd.
- `<repo-path>` — single-repo mode targeting **any** workspace repo checkout by workspace-relative path. Validate by existence — `<workspace-root>/<repo-path>/.git` must exist (dir for a clone, file for a worktree). No fixed whitelist.

Full procedure — repo discovery, worktree baseline, staging, commit, push, `glab mr create`, guardrails, reporting shape (5-line block for single-repo scopes; markdown table with `Repo | Branch | Status | MR | Reason` for multi-repo scopes; header line, totals, `**Failures**` sub-section, clean-repos collapse rule) — lives in [`skills/mr/SKILL.md#open`](../skills/mr/SKILL.md#open).

### Refusal conditions

- Scope arg missing or not one of `touched` | `all` | `current` | `<repo-path>` → stop and ask.
- `current` scope and cwd is not inside any workspace repo → stop and ask.
- `<repo-path>` scope and the path does not exist or is not a git checkout → stop and ask.
- Candidate branch is a protected branch (per workspace git standards — typically `main` / `staging` / `develop`) → skip that repo with a clear reason; never commit on a protected branch.
- `glab` missing / unauthenticated → surface the exact error and stop the whole batch; no `gh` fallback.
- Nothing staged and nothing to stage after inspecting the diff → skip with "nothing to commit"; never an empty commit.
- Single-repo scope with only a clean default branch → stop with "nothing to commit" instead of producing the table.

## ship

Runs the full `open` flow (Steps 1-4 and Reporting), then continues with the merge + sync + cleanup tail. Everything in `open` applies verbatim.

### Argument

`/mr ship <touched|all|current|<repo-path>>` — same scope grammar as `open`.

Full procedure — the merge phase (wait-for-mergeable, `glab mr merge <iid> --squash --remove-source-branch --yes`, sync via main-checkout `git checkout <default> && git pull --ff-only`, cleanup via `git worktree remove` + `git branch -d`), reuse-not-duplicate rule for already-open MRs, and the `ship`-mode reporting deltas (`**merged**` / `opened (blocked)` / `skipped` / `**failed**` status, extra `HEAD` column with the new default-branch SHA, failure stages widened to `commit` / `push` / `open` / `merge` / `pull` / `cleanup`, single-repo 5-line block replaces `Worktree:` with `Merged: <sha>`) — lives in [`skills/mr/SKILL.md#ship`](../skills/mr/SKILL.md#ship).

### Refusal conditions

- Every `open` refusal above applies verbatim.
- MR is blocked (CI failing, discussions open) → surface the blocker, skip the merge for that repo, keep going with the others. **Never force-merge.**
- MR already open for the source branch → **reuse it**; never open a duplicate.

## format

The operative reference for branch name, commit subject, MR title, MR body shape, mirror/hotfix variants, hard rules, and the pre-flight self-check. Other commands and skills load this via `[[mr]]` before authoring any MR body.

Full ruleset — pre-flight chain, §1.1 branch/commit types (`document` / `bugfix` / `fix` / `test` / `CICD` / `feature` / `maintenance` / `release` / `experiment` — priority order, first match wins), §1.2 branch scopes per repo family, §1.3 commit subject rules, §2 per-repo target branch (`git symbolic-ref` resolution — do not hardcode), §3 title = subject character-for-character, §4 body template with `## TLDR` / `## Summary` / `## Test Plan` / `## Validation` (Validation ≥ 3 rows on surface change), §4.1 conditional sections (migration / UI / feature-flag / auth-PII), §4.2 Mirror MR (first bullet of TLDR: `**Mirrors:** [repo!N](url).`), §4.3 Hotfix MR (last bullet: `**Hotfix paired MRs:** !A (→…), !B (→…).`), §5 `glab mr create` invocation, §6 `fix/*` multi-MR fan-out per the promotion chain declared in `<workspace-root>/tech/docs/standards/git.md`, §7 hard rules, §8 self-check — lives in [`skills/mr/SKILL.md#format`](../skills/mr/SKILL.md#format). Standards behind it: `<config-dir>/standards/git.md` (cross-repo baseline) + `<workspace-root>/tech/docs/standards/git.md` (engineering deltas). If this section and the standards ever drift, the standards win.

### Pre-flight chain (branch → commit → title → body)

```
branch:   <type>/<scope>/<2-4-word-description>
commit:   <type>(<scope>): <imperative subject>           ≤ 50 chars soft / 72 hard
title:    <commit subject>                                literally identical
body:     four sections — TLDR / Summary / Test Plan / Validation
```

If those four don't line up cleanly, fix the *branch* first — everything cascades.

### MR body layout (four required sections, headings verbatim)

```markdown
## TLDR

- **Problem:** one line — what's wrong or what's needed.
- **Solution:** one line — what this MR does.
- **How to validate in under 1 minute:** exact steps a reviewer runs.
- **Merge Risk Score:** High / Medium / Low
- **Hotfix paired MRs:** (engineering-only — `fix/*` MRs) cross-link the set, e.g. `!123 (→develop), !124 (→staging)`. Omit on non-hotfix MRs.

## Summary

What changed and why (bullets).

## Test Plan

What was tested locally and what the reviewer should test.
- Engineering: run / lint / type / suite commands and outcomes.
- Docs / design: render preview, link check, screenshot diff.

## Validation

| # | Action | Expected | Actual |
|---|--------|----------|--------|
| 1 | ... | ... | ✅ / ❌ |
| 2 | ... | ... | ✅ / ❌ |
| 3 | ... | ... | ✅ / ❌ |
```

Mirror MRs lead `## TLDR` with `**Mirrors:** [repo!N](url).` as the first bullet. `fix/*` hotfix MRs end `## TLDR` with `**Hotfix paired MRs:** !A (→…), !B (→…).` as the last bullet. Full variant examples, conditional-section triggers, `fix/*` fan-out table, and the pre-flight self-check → [`skills/mr/SKILL.md#format`](../skills/mr/SKILL.md#format).

### Refusal conditions

- `format` takes no argument — extra args → refuse with the offending value named.
- Any self-check line fails (branch shape, target branch, subject bounds, title mismatch, missing body section, Validation under 3 rows on a surface change, Mirror/Hotfix bullet missing, staged files include secrets or drift, `feature/*` diff without a `tests/` file) → fix before opening; never open the MR with the failure live.
